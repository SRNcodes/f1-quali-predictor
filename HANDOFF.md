## What this project does

Predicts Formula 1 qualifying results (each driver's lap time / pace) for
**any upcoming Grand Prix**, not just one specific race. It is NOT
hardcoded to one circuit — the pipeline is designed to be re-run for
whichever race is next on the calendar.

### Core idea (already implemented, works)

Raw lap times aren't comparable across circuits or years (different track
lengths, weather, tire rules), so instead of predicting raw lap time we
predict each driver's **"pace delta to pole"**: how many seconds slower than
the fastest time in that session they qualify. This normalizes everything so
form is comparable across circuits/years, then we convert back to a real lap
time using last year's pole time at that same circuit as the anchor.

### Data source

**Jolpica-F1 API** (`https://api.jolpi.ca/ergast/f1`) — free, no API key, the
community-maintained successor to the now-shutdown Ergast API. Has
qualifying results, race results, standings back to 1950. Not "FastAPI" (that's
unrelated — a framework we'll use later to *serve* the model).

Key endpoints already used:
- `/{season}/qualifying.json` — season's qualifying results (Q1/Q2/Q3 times)
- `/{season}.json` — season's race calendar (used to auto-detect the next race)

### How circuit-agnosticism works (IMPORTANT — just added, verify it)

`fetch_data.py --circuit <id>` fetches data for a specific circuit (e.g.
`baku`, `monza`, `silverstone` — these are Ergast/Jolpica circuitIds).

If `--circuit` is omitted, `get_next_race()` in `jolpica_client.py` calls the
season calendar endpoint and picks the next race whose date is today or
later, so the pipeline can just be re-run as-is before any race weekend
without me manually specifying the circuit each time. **This was just added
and should be tested end-to-end** — verify `get_next_race()` correctly picks
up the next race and that the full pipeline (ingestion -> features ->
training) runs cleanly with no `--circuit` flag passed.

### Feature set (in `features/build_features.py` and `training/train.py`)

- `driver_season_avg_delta` — driver's average pace delta this season so far
- `driver_recent_avg_delta` — same, but only last 3 races (captures recent form/momentum)
- `constructor_season_avg_delta` — team's average pace delta this season
- `driver_baku_last_year_delta` — **NOTE: variable name says "baku" but this is
  meant to generically mean "driver's pace delta at THIS circuit last year."**
  Rename this to `driver_circuit_last_year_delta` for clarity when you touch
  this code — it's a leftover from when this was Baku-specific.

### Models compared

Ridge, RandomForest, XGBoost, GaussianProcess — cross-validated with 5-fold
CV, best one auto-selected by mean absolute error. Each model's result now
also reports **standard error of the mean (SEM = std / sqrt(n_folds))**
across the folds, plus a rough 95% CI (+/- 1.96 * SEM), so you can see not
just "how big is the error" but "how much does that error estimate itself
wobble." With only 5 folds the SEM is itself a noisy estimate — don't over-index
on small differences between models until there's more data (more races run
this season = more folds worth trusting).

## Recently added (verify these work, then keep extending them)

- **`tests/test_features.py`** — pytest suite guarding against data leakage in
  `build_training_set()`. Run with `pytest tests/`. If you ever touch the
  leak-free logic in `features/build_features.py`, these tests must still
  pass — they're the single most important safety net in this repo.
- **`monitoring/log_prediction.py`** — logs each race's predicted qualifying
  order to `monitoring/prediction_log.csv` before the race, then scores it
  (pole prediction correct? mean position error?) once real results are in.
  This builds a real track record over time, which is a much stronger "does
  this actually work" signal than cross-validation alone. Usage is in the
  file's docstring. Extend this: right now scoring must be triggered
  manually after a race — eventually this should be a Kubernetes CronJob
  that checks for new results automatically.
- **`features/weather.py`** — fetches historical precipitation via the free
  Open-Meteo API. **Not yet wired into `build_features.py`** — needs circuit
  lat/lon (Jolpica's race calendar endpoint has this per circuit, see
  `Circuit.Location` in the raw API response) merged in as a feature.
  Also note: this module fetches HISTORICAL weather for building training
  features. For the upcoming race itself, you need a FORECAST API instead
  (Open-Meteo has a free one) since the race hasn't happened yet. Don't
  conflate the two — wire up forecast separately for prediction-time use.
- **Practice session pace — NOT implemented, and can't be via Jolpica.**
  Jolpica/Ergast never tracked FP1–FP3 lap times; that data isn't in their
  schema. To add this, you'd need the `fastf1` Python package, which pulls
  from a different F1 timing data source. This is real added complexity
  (different data source, different auth/rate-limit behavior) — don't fake
  or approximate this feature, implement it properly with fastf1 or skip it
  and note the limitation in any writeup.

## Ground rules for this project

- Prioritize teaching/explaining over silently doing — I want to actually
  understand Docker/K8s/AWS, not just have a working repo.
- Every pipeline stage should stay circuit-agnostic. Don't reintroduce
  Baku-specific hardcoding when extending this.
- Keep the leak-free training approach (only use prior-race data to predict
  a given race) — don't let future information leak into features.

  that idles (e.g. avoid always-on SageMaker endpoints); flag anything that
  could rack up meaningful cost before creating it.
